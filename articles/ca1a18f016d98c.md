## テキストを生成しないAI「Jev」の登場

2026年9月15日、TypeSafe AI というラボが「Jev」というモデルを公開しました。

普通のLLMと違って、**Jevはテキストを生成しません**。

判断の対象（state）と、型のついた質問を渡すと、答えが確率つきで返ってきます。
```
state:    「注文をキャンセルして今すぐ返金してほしい」
question: この問い合わせを担当する部署は? (billing / technical / sales)
answer:   billing (確率 0.87, confidence 0.82)
```
特徴は大きく3つで、 **「高速・安価・そこそこ賢い」** 。
公式は「フロンティアモデルの40〜200倍速い」と言っています。そして構造上、選択肢にない答えを返すことができません。

公式SDKは Python と JavaScript の2つ(どちらも動的型付け言語......)。

私は普段Kotlinで開発をしているので、自分のプロダクトに組み込むにはHTTP を直接叩くか、誰かが書いたクライアントを使うことになります。

そこで、気づいたことがあります。

**TypeSafe という名前の会社の API なのに、Kotlin 側が全然 type-safe じゃない！**

返ってくるのは `String`。それを `when` で分岐して、`else` を書いて、どこかでキャストする。Kotlin の型システムがほとんど仕事をしていません。

というわけで、自作のライブラリをつくりました。[kojev](https://github.com/ItisNoMatter/kojev) という Kotlin Multiplatform 向けのクライアントです。

https://x.com/iNoma_main/status/2102366209878765761?s=20

```kotlin
implementation("io.github.itisnomatter:kojev:0.1.0")
```

## Jev の3つのプリミティブ

Jev に投げることのできる質問は3種類だけです。

| 型 | 問い | 返ってくるもの |
|---|---|---|
| **Choice** | 選択肢から1つ選ぶ | 選ばれたラベル、全選択肢の確率分布、confidence |
| **Score** | 2〜10段階のルーブリックで採点 | スコア、レベルの凡例、確率分布、confidence |
| **Noul** | 「この記述は真か?」 | **0〜1の確率そのもの。confidence は無い** |


### 主用途は「1回でまとめて訊く」

Jev の設計でいちばん重要なのはここです。**1つのリクエストに入れた質問は、同じ state に対して並列に評価されます。**

state は1回しか送られません。質問を追加しても、増えるコストはその質問自身のトークン分だけ。

LLM を使ったワークフローでは、「1つ訊いて、答えを見て、次を決める」と逐次的に進めがちですが、Jev では発想が逆になります。**訊けるものは先に全部訊いて、分岐はコードでやる。** [公式が "speculative fan-out"（使うかわからない質問もまとめて投げて、コード側で捨てる）というパターンを勧めている](https://docs.typesafe.ai/patterns/fan-out)くらいです。

クライアントライブラリは、「複数の質問を一度に投げる」のが自然に書ける形であるのが理想です。そして、Kotlinにはその表現力があると私は判断しました。

## `String` が返ってくると何が困るか

素朴に書いた例を以下に示します。

```kotlin
val answer: String = result.choice("team")   // "billing" | "technical" | "sales"

when (answer) {
    "billing" -> routeToBilling()
    "technical" -> pageOnCall()
    "sales" -> routeToSales()
    else -> {}   // ← ここ
}
```

3つの困りごとが発生します。

**`else` が必ず要る。** コンパイラは `answer` が3通りしかないことを知らないので、網羅性チェックが効きません。そして人間は `else -> {}` と書いてしまう。

**選択肢を足したときに何も起きない。** 例えば`"vip"` を追加して、criteria には書いたけれど `when` の更新を忘れた場合、コンパイルが通ってしまいます。実行時には `else` で回収され、実装漏れに気づくのは困難です。

**typo が実行時まで出ない。** `"techincal"` と書いても誰も教えてくれません（IDEが警告を出すケースはあるでしょうが）。

どれも Kotlin 使いが `enum` で解決してきた問題です。せっかくリッチな言語機能があるのですから、活用しましょう。

## kojev の書き味

kojev では、**選択肢は利用者が定義した `enum` そのもの**です。

```kotlin
enum class Team(override val description: String) : Criterion {
    BILLING("Payments, invoicing, refunds"),
    TECHNICAL("Bugs, outages, integrations"),
    SALES("Pricing, upgrades, new accounts"),
}
```

`Criterion` は `description` を1つ持つだけのインターフェースです。説明文を enum 定数に持たせているのがポイントで、**定数を足して説明を書き忘れるとコンパイルが通りません。**

Jev に渡す criteria（ラベル→説明のマップ）と、Kotlin 側の型が、同じ場所で1回だけ定義される。二重管理が発生しません。

### 複数の質問を一度に投げる

```kotlin
enum class Urgency(override val description: String) : Criterion {
    LATER("Not time-sensitive"),
    TODAY("Should be handled today"),
    NOW("Needs immediate attention"),
}

// 質問は値。一度宣言して、毎リクエスト使い回す
val teamQ = choice<Team>("team", "Which team should handle this ticket?")
val urgencyQ = score<Urgency>("urgency", "How urgently does this need a response?")
val angryQ = noul("is_angry", "Is the customer expressing anger?") {
    whenTrue = "Clear irritation or forceful tone"
    whenFalse = "Neutral or calm"
}
val churnQ = noul("churn_risk", "Is the customer hinting they might cancel?")

// リクエストは1回。4つの質問が同じ state に対して並列に評価される
val result = jev.decide(ticket) {
    ask(teamQ, urgencyQ, angryQ, churnQ)
}

val team: Team = result[teamQ].value
val urgency: Urgency = result[urgencyQ].mostLikely
val angry: Double = result[angryQ]
val churn: Double = result[churnQ]

// 振り分けはコード側。閾値も自分で決める
if (result[teamQ].confidence < 0.8 || angry > 0.8 || churn > 0.6) {
    escalateToHuman(result.requestId)
} else {
    when (team) {
        Team.BILLING -> routeToBilling()
        Team.TECHNICAL -> if (urgency == Urgency.NOW) pageOnCall() else queue(team)
        Team.SALES -> routeToSales()
    }
}
```

Kojevがもたらす恩恵は以下の通りです。

**`when (team)` が網羅チェックされる。**　`Team` に定数を足したら、この `when` はコンパイルエラーになります。`else` は要りません。

**`QuestionKey<T>` が答えの型を運んでいる。** `result[teamQ]` は `ChoiceAnswer<Team>`、`result[urgencyQ]` は `ScoreAnswer<Urgency>`、`result[angryQ]` は `Double`。同じ `result` から引いているのにキーごとに違う型が返り、キャストは一度も要りません。

**文字列キーでの取得は提供していません。** `result["team"]` のような API は、補助としても用意していません。理由は後述します。

### state も型で渡せる

`decide` の第1引数は `@Serializable` な値なら何でも通ります。

```kotlin
@Serializable
data class Ticket(val subject: String, val body: String, val plan: String)

val result = jev.decide(ticket) { ask(teamQ) }
```

state が文字列しか受け取らないと、**利用者が自分でドメインオブジェクトをテキスト化することになる**からです。

```kotlin
// 型がない世界
jev.decide("plan=$plan, subject=$subject, body=$body") { ... }
```

そして重要なのは、**Jev はそのテキスト化した結果を読んで判断している**ということ。区切り文字も、フィールド名を入れるかも、順序も、全部が精度に影響します。ここはライブラリが引き受けるべき責務だと思いました。

`@Serializable` なら JSON のオブジェクトになり、フィールド名がそのままモデルへのラベルとして届きます。`@SerialName` で言い換えることも、`@Transient` で判断に無関係な内部 ID を落とすこともできます。[公式が公開している「モデルの弱点」ドキュメント](https://docs.typesafe.ai/model-jaggedness/jev-1.13#large-state-full-of-irrelevant-detail)には「無関係な内容が混じると精度が下がる」とあるので、`@Transient` は飾りではなく精度の道具です。

> Accuracy falls as the state grows with content unrelated to the decision. Unrelated detail acts as a distractor, and a large state makes it harder to tell which part of the input produced a wrong answer.



入力も出力も型。間に文字列が一度も現れない、というのが kojev の形です。

## 設計で迷ったところ

ここからが本題かもしれません。作る過程でいちばん時間を使ったのは、コードを書くことではなく「何を入れないか」を決めることでした。

### Score の平均を丸めるヘルパーを入れなかった

Score の答えは `score` という Double で返ってきます。これは**レベル番号の確率加重平均**です。3段階なら 0〜2 の間の値になる。

素朴に考えると、これを丸めて「結局どのレベルなの?」を返すヘルパーが欲しくなります。`nearestLevel` のようなものです。実際、他のクライアントは提供しています。

入れませんでした。実 API に投げて返ってきた、これを見たからです。

```
"The export button crashes the settings page in Safari."

  distribution:  COSMETIC 0%, DEGRADED 49%, BLOCKING 51%
  score:         1.51
  mostLikely:    BLOCKING
```

`DEGRADED` と `BLOCKING` がほぼ半々です。平均は 1.51。これを丸めて `BLOCKING` とだけ返したら、**モデルが「半分は DEGRADED だと思っている」と言っている情報が消えてしまいます。** これは良くない。

もっと悪い例も作れます。`{COSMETIC: 0.5, DEGRADED: 0.0, BLOCKING: 0.5}` なら平均はちょうど 1.0。丸めると、**モデルが確率 0% と言ったレベルが返ります。**

しかも、[公式が公開している「モデルの弱点」ドキュメント](https://docs.typesafe.ai/model-jaggedness/jev-1.13#math-using-score)には「スコアの出力（期待値や確率など）を、評価基準の2つのレベルの間における数値の正確な大きさを算出するために使用しないでください。」と明記されています。平均を1つのレベルに落とすのは、ライブラリが round / floor / argmax のどれかを勝手に選ぶということで、それは利用者の判断を奪う行為です。

なので `ScoreAnswer` はこうなっています。

```kotlin
class ScoreAnswer<T> {
    val score: Double            // 平均。レベルそのものではない
    val mostLikely: T            // 最頻値
    val probabilities: Map<T, Double>
    val confidence: Double
}
```

`value` という名前のプロパティを**置いていません**。Choice には `value` があるので非対称ですが、これは意図的です。「Score の答えは単一のレベルではない」という事実を、そのまま型にした結果です。



### 閾値のデフォルトを置かない

`confidence > 0.8 なら自動処理、それ以下は人間へ` という「confidence-gated routing」は Jev の代表的なパターンです。

便利なので、ライブラリ側に `isTrue(threshold = 0.7)` のようなヘルパーを用意したくなります。

これはやめました。**デフォルト値があると、それが妥当かを考えずに使われるから**です。0.7 が正しい閾値かどうかは、何を判断しているか、間違えたときに何が起きるかで変わります。返金の自動承認と、メールの仕分けで、同じ閾値とは限りませんからね。

kojev は確率と confidence を素直に返すだけで、そこから先は書く人の仕事にしました。

### 文字列キーでの取得を提供しない

`result["team"]` があれば便利です。`QuestionKey` を変数に持ち回らなくていい。

これも入れませんでした。**あれば必ずそっちが使われるから**です。

型安全な入口と、そうでない入口を両方用意すると、人は楽なほうを使います。そして楽なほうは、このライブラリの存在理由そのものを無効にします。補助 API としても提供しないと決め、型安全性を追求しました。

### 必須のものは引数、任意のものはラムダ

DSL を作るとき、最初はこう書こうとしていました。

```kotlin
val intentQ = choice<Intent>("intent") {
    instructions = "Which team should handle this?"   // ← 書き忘れたら?
}
```

ラムダの中の `var` は、**代入されないまま抜けられます。** つまり `instructions` を書き忘れると、実行時の `require` でしか捕まらない。

なので必須のものは引数にしました。

```kotlin
val intentQ = choice<Intent>("intent", "Which team should handle this?")
```

これなら書き忘れはコンパイルエラーです。`Criterion` で説明文を必須にしたのと同じ発想で、DSL 全体にこの原則を通しています。結果として Choice の主形式にはラムダが1つも出てきません。

宣言的であることと、ブロックで書くことは、別の話だと思っています。`Text("Hello")` にラムダが無くても Compose は宣言的です。

## `baseUrl` がローカルモデルへの扉になった話

kojev には最初から `baseUrl` を差し替える口があります。

入れた理由は、実はかなり後ろ向きなものでした。**API キーをアプリに埋め込めないから**です。公式 SDK はブラウザからの直接利用を禁止していて、理由はキーの露出。同じ理屈でモバイルアプリからの直叩きも本番では無理なので、自前プロキシ経由を一級の使い方として想定する必要がありました。

ところが、これが別の意味を持ちました。

Kotlin Slack で Jev の話題が出たとき、議論の中心は「ホスト型の Jev」ではなく**ローカルで動く open-weight モデル**に移っていきました。Laya、Qwen-RLCD、OpenJev。「有料のホストサービスに依存したくない、ローカルで動かせる KMP ライブラリが欲しい」という声が複数ありました。

そこに [pambrose/laya-server](https://github.com/pambrose/laya-server) が現れます。**Jev の API を、ローカルの Laya チェックポイントで実装した PoC** です。

`baseUrl` を向けるだけで動くのでは? と思ったので、試しました。

**Maven Central に公開した 0.1.0 を、両方とも無改造で動かせました。**

```
state    : "I was charged twice for August. Please fix this ASAP."

intent   : REFUND   confidence=0.569
           REFUND=0.865, TECHNICAL=0.101, OTHER=0.034
is_angry : 0.861
urgency  : mostLikely=NOW   score=1.806   confidence=0.522
           LATER=0.029, TODAY=0.137, NOW=0.835
```

面白かったのは、**kojev のパースが厳格なまま通った**ことです。kojev は、返ってきた確率分布のキーが送った選択肢と完全一致しなければ例外にします。欠損も型不一致も範囲外も、黙ってデフォルト値には落としません。それが一度も引っかからなかった。つまり laya-server の実装が本当に忠実だということです。

正直に書いておくべき数字も出ました。**温まった状態で 1.7〜2.0秒**（Windows、Ryzen AI 5 330、CPU 推論、GPU なし、english チェックポイント）。Jev が謳う 70〜500ms とは桁が違います。

laya-server の README 自身も制約を明記しています。コンテキスト長は Jev の 32k に対し 512〜1024。`input_tokens` の数え方が違うので比較できない。そして答えの質は別物です。

型安全な契約はそのまま持ち運べたが、中身のモデルは別物だった、ということになります。

キーの都合で入れた機能が、結果的に「ベンダーに縛られない」という強みになりました。

## 先行実装について

最後に、正直に書いておきたいことがあります。

公開の準備をしていたとき、[pambrose/jev4k](https://github.com/pambrose/jev4k) を見つけました。**僕が開発に着手した日の夕方に、独立に、ほぼ同じ発想で作られ公開された Kotlin クライアント**です。Choice の答えを利用者の enum で返し、説明を持たせるインターフェースがあり、`@Serializable` な state も受け取る。

正直、見つけたときはかなり落ち込みました。「唯一の差別化点」だと思っていたものが、唯一ではなかったからです。

https://x.com/iNoma_main/status/2102269461911015651?s=20

ただ、独立に同じ設計へ辿り着いたということは、**Kotlin で Jev を扱うならそれが自然な形だ**ということでもあります。そう考えることにしました。（先を越されたのはすごく悔しいですが！！！！）

方針の違いは残ります。

- **jev4k** は JVM 向けで、便利機能が充実しています。文字列 ID での取得、閾値つきのヘルパー、Score の平均を丸めるメソッド、テスト用のフェイク、Java からの利用。ドキュメントサイトもある。**JVM のみで使う前提なら、こちらのほうが実用的な場面は多いはずです。**
- **kojev** は Kotlin Multiplatform（JVM / Android / iOS）で、Score のルーブリックも enum、そして上に書いたとおり「型付きの読み方が1つしかない」ことを優先しています。iOS / Android ターゲットがあるのは型と DSL を共有するためです。レアケースですが、ユーザがキーを入力するようなBYOK型のアプリにも対応できます。

どちらが良いという話ではなく、何を優先したかの違いです。

ちなみにもう1つ、[ufec/typesafe-sdk-kotlin](https://github.com/ufec/typesafe-sdk-kotlin) という公式 JavaScript SDK の忠実な移植もあります。公式の挙動をそのまま欲しいならこちらです。

テスト用のフェイクが jev4k にあったのは、なるほどと思いました。kojev は `Decision` の構築が internal なので、利用者が自分のコードをテストするときに偽の結果を組み立てられません。型付きのまま提供できるはずなので、ここは入れたいと思っています。あとは Dokka での API ドキュメントもですね。

## まとめ

- Jev はテキストを生成せず、型付きの判定を確率つきで返すモデル
- 1リクエストに複数の質問を入れて、同じ state に並列評価させるのが主用途
- kojev は、その答えを利用者が定義した `enum` で受け取る Kotlin Multiplatform クライアント
- 丸めない、閾値を決めない、文字列で引かせない。**判断は書く人のもの**という方針で作った
- `baseUrl` を差し替えれば、ローカルの open-weight モデルにも向けられる

```kotlin
implementation("io.github.itisnomatter:kojev:0.1.0")
```

https://github.com/ItisNoMatter/kojev

なお、本プロジェクトは非公式であり、TypeSafe AI, Inc. とは提携・承認関係にありません。
